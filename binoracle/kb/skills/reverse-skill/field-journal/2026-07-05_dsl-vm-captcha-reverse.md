# Full Reverse Analysis of a Captcha System

## Scenario
Objective: Reverse-engineer a large captcha system to understand its complete working principle and validation process.

## Target Entities
- **nc.js** (72KB) — Webpack bundled slider core (9 modules)
- **fireyejs.js** (583KB) — DSL VM interpreter (26 opcode custom instruction set)
- **awsc.js** (9KB) — Module loader
- **secaptcha.js** (72KB) — WASM C compiled product (emscripten)
- **et_f.js** (262KB) — Another DSL VM type file

## Verified Technical Solutions

### Solution A: Selenium + CDP Drag-and-Drop (Recommended)
Send native mouse events using CDP `Input.dispatchMouseEvent` to complete the validation in a real browser.
- Success Rate: High
- Dependencies: Chrome + Selenium/Playwright

### Solution B: Playwright Headless Browser Runner
Load the DSL VM and module loader in Playwright, expose the token via HTTP API.
- Success Rate: Medium (depends on WASM initialization environment)

### Solution C: Pure Requests Protocol Validation
Directly call API endpoints through HTTP requests for validation.
- Success Rate: **Very Low** (token strongly bound to browser TLS/IP/fingerprint)
- Not recommended

## Key Discoveries

1. **Token cannot be used outside the browser** — The token generated by the DSL VM is validated on the server side for context consistency (TLS JA3, IP, Cookie, Referer, etc.)

2. **fireyejs.js is not a WASM binary but a DSL VM** — A 583KB pure JS implementation of a custom virtual machine, executed through a loop of an interpreter that interprets encoded instructions using 26 opcodes

3. **nc.js 9 modules fully reversed** — Includes API endpoints, slider UI, interaction logic, ncSessionID algorithm, multilingual support, etc.

4. **The true WASM compiled product is secaptcha.js** — 72KB, uses SharedArrayBuffer + Atomics, emscripten compiles C code

## Pitfalls Encountered

1. Testing with a test appkey does not trigger real validation; must use the appkey from the actual page
2. `initialize` returns a specific status code to indicate slider mode; returning `success` only confirms session creation
3. JSONP request URLs in performance logs may be captured incompletely due to script tag injection methods
4. Exported function names do not exist in the DSL VM file (encoded by the VM); true exports are exposed through the module registration center

## Reusable Patterns

- **DSL VM Reverse Engineering Pattern**: `case extraction → opcode classification → constant table analysis → function tracing → export extraction`
- **General Architecture of Captcha Systems**: `Entry JS → Module Loader(WASM/DSL) → API Communication Layer → Frontend UI → Server-side Validation`
- **Native Event Bypass with CDP**: `Input.dispatchMouseEvent` bypasses detection, unrelated to WebDriver

## Toolchain

- Selenium + CDP: Browser automation + native mouse events
- Playwright: Headless browser + route interception
- Python requests: Pure API calls (validation fails)
- Node.js + Playwright: Runner service
