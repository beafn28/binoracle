# Abstract

The target is a C++-written NaN-boxing toy interpreter (glibc 2.27, PIE / Full RELRO / NX / Canary). The only vulnerability lies in the `BinOp` operation result not being truncated to 48 bits, allowing for forging object headers to achieve forward arbitrary heap read/write, ultimately through tcache poisoning to hijack `__free_hook` to `system` for shell.

## Verifiable Constants

- Environment: glibc 2.27, PIE / Full RELRO / NX / Canary
- Encoding of constants: High 16 bits == `0x1337` → Object Handle, Low 48 bits = arena object header heap address; Otherwise, a 48-bit integer.
- Object Header: `key ^ (0xBEEF<<48 | nchildren)`
- Numeric Leaves: `key ^ (val & 0xFFFFFFFFFFFF)`
- Final flag: `flag{f2ab8ac8-cd80-4c45-b859-ae6ba9289959}` (rotates per instance)

## Standard Solution Workflow

1. **Vulnerability Identification**
   - `BinOp_eval` is the only path not truncating results to 48 bits.
   - Arbitrary high 16-bit values can be constructed: `$1=0x1337; $2=0x1000000; $1=$1*$2; $1=$1*$2` → `env[1] = 0x1337<<48`.
   - Forging object headers: `$k = 0xBEEF<<48 | len`.

2. **Forging Long Object Headers → Forward Arbitrary Heap Read/Write**
   - Create a true object `$0=[0,0]`, use BinOp to create `hdr = 0xBEEF<<48 | 0x6000`.
   - Write into the first leaf of `$0` using `SetField`.
   - `$0[0][k]` can read/write from `arena + 16 + 8*k` (k < 0x6000).

3. **Information Leakage (1-bit Oracle)**
   - No printing functionality, reading bits through successful/`runtime error!`/`invalid syntax!` states.
   - Method: `(v>>i)&1` to set `0x1337` tag and cause a `runtime error` from BinOp due to the right operand being an object handle → This bit is 1.
   - Leaking key: `$dst=$0[0][1]` reads uninitialized slot → `0 ^ key = key`.
   - Leaking arena/libc: `k=8193` (heap self-pointer), `k=8205` (libc pointer to `_IO_2_1_stderr_`).

4. **tcache 0x20 fd Poisoning → `__free_hook = system`**
   - Using `write1` to change the file descriptor of a freed chunk at address 0x20 to `__free_hook`.
   - Attack command `$4=$0[<system decimal>]`: The index is pushed onto a `std::vector`, which takes an 8-byte buffer from tcache bin 0x20.
   - If the buffer lands on `__free_hook`, then `buffer[0] = index = system`.

5. **Two Decisive Pitfalls**
   - **15-bit indices are 2-pop, not 3-pop**: The libc address is always 15 bits and falls within libstdc++ SSO boundary, so no temporary string allocation for the 15th character. Debugging with ≥16-bit numbers will fall into the 3-pop branch, misjudging the target.
   - **The trigger must be a 0x30 allocation, not a 0x20**: After setting `__free_hook` to `system`, it resides at the head of the 0x20 bin chain. If the trigger is 16 characters (0x20 allocation), its `std::string` will allocate a 0x20 chunk, popping out `__free_hook` into the buffer, which can be overwritten with `/bin/sh` to cause a crash. Use a 24-39 character 0x30 allocation line instead (e.g., `/bin/sh #` + 22×`A` = 31 characters).

6. **Reading Flags**
   - Remote minimal chroot has no `cat`, `id`, `head`, or `grep`, only `ls` and `/bin/sh`.
   - Use the dash's built-in `read a < flag; echo "$a"` to read out.
