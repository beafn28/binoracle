Architecture

binoracle is built as a layered, modular Python package. Each layer has a single responsibility — the CLI wires them together, but every component can be imported and used independently.

Figure 1 — Component map. Solid arrows = primary data paths. Dashed arrows = optional/lazy paths.

Components at a glance

Architecture Diagram

The diagram above shows two main pipelines flowing through the architecture:

  1. CVE Pipeline — CLI → CVE Agent → Oracles + LLM + Docker → Report + Store
  2. Binary RE Pipeline — CLI → Workflows → Oracles + LLM → Findings → Report

Both pipelines share the same LLM backend, session store, RAG corpus, and HTML report generator. The MCP server wraps every tool and exposes it to AI assistants like Claude.

Data Flow

When you run binoracle cve CVE-2024-1234 -o report.html, the following happens:

  1. cli.py parses the command and calls cmd_cve(args, config).
  2. investigate_cve() in cve_agent.py starts. It fetches the CVE from NVD, extracts CVSS score, severity, vector and description.
  3. The LLM backend is queried for a hypothesis: target binary, trigger input, vulnerability class, affected version, attack plan.
  4. If a public PoC exists on GitHub, it is fetched and read. The hypothesis is updated with real data.
  5. The source code of the target is downloaded (PyPI, npm, GitHub) and statically analysed with radare2 / grep / AST analysis to ground the hypothesis in real function names and line numbers.
  6. A Docker Compose lab is scaffolded and started. The PoC script is executed inside the sandbox. Output, screenshots and HTTP responses are captured.
  7. The Investigation dataclass is populated with all evidence and serialised to cache (~/.cache/binoracle/investigations/).
  8. render_investigation() generates the markdown report. render_investigation_page() wraps it in the professional HTML template.
  9. The HTML is written to the path you passed with -o. The terminal shows only the verdict box and the saved-path confirmation.

CLI Layer

binoracle/cli.py is the single entry point. It defines subcommands using argparse subparsers:

binoracle cve <CVE-ID> [-o report.html] [--json evidence.json]
binoracle investigate <CVE-ID> [--binary elf] [-o report.html]
binoracle cve-chain <CVE-ID> [<CVE-ID> ...]
binoracle autopwn <binary> [-o report.html]
binoracle decompile <binary> [-f func] [--engine ghidra|r2]
binoracle triage <binary>
binoracle hunt <binary>
binoracle firmware <image> [--extract-to dir]
binoracle kernel-exploit <module.ko>
binoracle finetune --collect | --train [--adapter lora]
binoracle mcp-server

Each subcommand handler (cmd_cve, cmd_autopwn, …) is a plain function that takes (args, config) and returns nothing. The exit code is set by sys.exit() only on explicit errors.

The config object is built from environment variables and ~/.config/binoracle/config.toml. No config file is required — sensible defaults apply for everything except the LLM backend URL.

Agent Layer

workflows/cve_agent.py is the largest file (~4500 lines). It contains:

  • The Investigation dataclass — the central data model for a CVE investigation.
  • investigate_cve() — the main orchestrator. It is a plain function, not a class. All state lives in the Investigation object passed by reference through helpers.
  • All the step functions: fetch_cve(), query_llm_hypothesis(), fetch_public_poc(), ground_in_source(), scaffold_lab(), run_poc(), capture_screenshots(), render_investigation().
  • The investigation cache (read/write JSON to ~/.cache/binoracle/investigations/).

The agent never calls the CLI or the MCP server. It only knows about the Investigation dataclass and the step functions. This keeps it testable in isolation.

Oracle Layer

Oracles are thin wrappers around external tools that return structured data:

  • oracles/r2session.py — manages a persistent r2pipe session. Runs radare2 JSON commands and caches results for the binary's lifetime.
  • oracles/checksec.py — parses r2 iS and r2 i output to extract NX, PIE, Canary, RELRO, ASLR.
  • oracles/angr_oracle.py — symbolic execution with angr. Used for auto-verification of stack overflows (finds exact overflow offset).
  • oracles/capstone_fallback.py — disassembly fallback when r2 is not installed.
  • oracles/pefile_oracle.py — PE header analysis (DllCharacteristics, imports, sections).
  • oracles/elf_oracle.py — ELF analysis via pyelftools (DWARF, symbol table, section flags).

All oracles are lazily imported — they only load when the tool they wrap is actually available. Missing an oracle never crashes binoracle; it degrades gracefully to what is installed.

Report Layer

report/html.py (~2500 lines) generates three kinds of self-contained HTML reports:

  • Binary RE report — render_html(): KPI dashboard, findings table, mitigation panel, decompiled functions, attack surface.
  • CVE investigation report — render_investigation_page(): CVE hero header, CVSS/status badges, metadata grid, full markdown evidence below.
  • Dataset SFT report — render_dataset_page(): summary + JSONL download button.

All reports are self-contained: fonts are loaded from Google Fonts, everything else is inline or base64-embedded. No internet connection is needed to open a saved report.

Session Store

store/session.py provides a lightweight append-only JSON store. Each Finding is a dataclass with title, severity, verdict, evidence, and location. Findings are written to ~/.local/share/binoracle/sessions/ and can be resumed across CLI invocations.

MCP Server

mcp_server.py exposes every binoracle capability as an MCP tool. The server uses the mcp Python package (FastMCP) and communicates over stdio. See the MCP Tools Reference for the full tool list.

Start the server with:

binoracle mcp-server
