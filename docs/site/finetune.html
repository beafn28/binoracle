LoRA Fine-tuning

binoracle can generate a supervised fine-tuning (SFT) dataset from your own CVE investigations and binary analysis sessions, then fine-tune a local LLM with LoRA adapters — producing a model that is significantly better at your specific technology stack and vulnerability classes.

LoRA Architecture

LoRA (Low-Rank Adaptation) adds a small number of trainable parameters to a frozen base model. Instead of updating all weights (which requires 40–80 GB of GPU RAM for a 7B model), LoRA injects trainable rank-decomposition matrices into the attention layers:

W' = W + BA   where B ∈ R^(d×r), A ∈ R^(r×k), r << min(d,k)

At inference time the LoRA weights are merged with the base model — no extra latency. For security-focused fine-tuning, rank r=8 or r=16 is typically sufficient.

ParameterTypical valueEffect
r (rank)8–16Higher = more capacity, more GPU RAM
alpha16–32Scaling factor (typically 2×rank)
Target modulesq_proj, v_projWhich attention matrices get LoRA
Dropout0.05Regularisation
Epochs3–5More = better fit, risk of overfitting on small datasets
Learning rate2e-4Cosine schedule with warmup

Dataset Generation

Every CVE investigation and binary analysis session binoracle completes is a potential training example. The finetune --collect command converts completed investigations into SFT examples in ShareGPT format:

binoracle finetune --collect --output sft_dataset.jsonl

# Options:
#   --min-cvss 5.0     Only include investigations with CVSS >= 5.0
#   --verified-only    Only include verified (confirmed) investigations
#   --include-binary   Include binary RE sessions (default: CVE only)
#   --lang es|en       Dataset language
#   --since 2024-01-01 Only include sessions since this date

Each collected session becomes one or more training examples. For a CVE investigation, binoracle generates:

  • A hypothesis example: system prompt + CVE description → target, trigger, attack plan
  • A PoC example: system prompt + CVE + grounded source analysis → PoC script
  • A verdict example: system prompt + CVE + lab output → verification verdict

For a binary RE session it generates examples for triage, vulnerability hypothesis, and exploit strategy.

finetune Command

binoracle finetune [--collect | --train | --merge | --push] [options]

Subcommands:
  --collect            Generate SFT JSONL from completed sessions
  --train              Train LoRA adapter on a JSONL dataset
  --merge              Merge LoRA adapter into base model (creates new GGUF)
  --push               Push merged model to Ollama local registry

Options (--collect):
  --output FILE        JSONL output path (default: sft_dataset.jsonl)
  --verified-only      Only include verified investigations
  --min-cvss N         Minimum CVSS score to include
  --since DATE         Only include sessions from this date onward

Options (--train):
  --dataset FILE       JSONL dataset to train on (required)
  --base-model NAME    Base model in Ollama (default: config llm.model)
  --adapter-name NAME  Name for the LoRA adapter (default: binoracle-lora)
  --rank N             LoRA rank (default: 8)
  --epochs N           Training epochs (default: 3)
  --lr FLOAT           Learning rate (default: 2e-4)
  --gpu N              Number of GPUs (default: auto-detect)

Options (--merge):
  --adapter NAME       Adapter to merge (default: binoracle-lora)
  --output NAME        Output model name in Ollama

Options (--push):
  --model NAME         Merged model to push

JSONL Format

The dataset uses ShareGPT format — the same format used by most open-source fine-tuning frameworks (LLaMA-Factory, Axolotl, Unsloth):

// sft_dataset.jsonl — one JSON object per line
{
  "conversations": [
    {
      "from": "system",
      "value": "You are binoracle, an autonomous CVE exploit researcher..."
    },
    {
      "from": "human",
      "value": "CVE-2024-1071: SQL injection in Ultimate Member WordPress plugin via the 'sorting' parameter. CVSS 9.8 CRITICAL. Affected: Ultimate Member <= 2.8.3."
    },
    {
      "from": "gpt",
      "value": "Target: WordPress with Ultimate Member plugin <= 2.8.3\nTrigger: HTTP GET /wp-json/um/v1/account?sorting=... with SQL injection payload\nClass: sqli (time-based blind)\nAffected table: wp_users\n..."
    }
  ],
  "source": "binoracle-investigation",
  "cve": "CVE-2024-1071",
  "cvss": 9.8,
  "verified": true
}

Full Workflow

A complete fine-tuning workflow from investigation to deployed model:

# Step 1: Run several CVE investigations to build up a dataset
binoracle investigate CVE-2024-1071 --source wordpress
binoracle investigate CVE-2024-27956
binoracle investigate CVE-2023-23752
# ... run 20-50 investigations for a useful dataset

# Step 2: Collect all verified sessions into a JSONL dataset
binoracle finetune --collect --verified-only --output my_dataset.jsonl
# Output: my_dataset.jsonl with N training examples

# Step 3: Train a LoRA adapter on the dataset
binoracle finetune --train --dataset my_dataset.jsonl --base-model qwen2.5-coder:7b --adapter-name my-lora --epochs 3
# This requires: a GPU with >=8 GB VRAM (or CPU with patience)
# Training takes ~30 min for 500 examples on a 7B model with one RTX 3080

# Step 4: Merge the adapter into the base model
binoracle finetune --merge --adapter my-lora --output binoracle-custom:latest

# Step 5: Use the fine-tuned model
BINORACLE_MODEL=binoracle-custom:latest binoracle cve CVE-2024-1234 -o report.html
GPU requirements: Training a 7B model with LoRA requires ~8 GB VRAM (quantised to 4-bit via bitsandbytes). Training a 13B model requires ~16 GB. Training a 34B model requires ~24 GB. CPU training is possible but very slow (~10× slower than GPU).
