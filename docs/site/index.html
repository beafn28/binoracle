Quick Start

Prerequisites: Python 3.10+, Docker 20.x+, Ollama 0.3+.

# 1. Install binoracle
pip install binoracle

# 2. Install Ollama and pull the model (Linux / macOS)
curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen2.5-coder:7b

# 3. Configure the LLM backend
export BINORACLE_BACKEND=openai
export BINORACLE_BASE_URL=http://127.0.0.1:11434/v1
export BINORACLE_MODEL=qwen2.5-coder:7b

# 4. Run the CVE engine on a real CVE
binoracle cve CVE-2025-27516

# 5. Analyse a binary
binoracle triage ./target_binary
Persist configuration. Add the three export lines to ~/.bashrc or ~/.zshrc so they survive shell restarts.

Two Pipelines

binoracle exposes two independent analysis pipelines that can be used separately or combined.

CVE Pipeline

Takes a CVE identifier. Retrieves the NVD descriptor, passes it to a local LLM which generates exploit hypotheses autonomously. Provisions an ephemeral Docker Compose lab, executes the proof-of-concept, records Playwright screenshots at every verification step, and emits a self-contained HTML report to disk.

No data is sent to external services. The LLM runs entirely on your machine via Ollama.

binoracle cve CVE-2025-27516
binoracle cve-batch CVE-2025-27516 CVE-2024-23334

Binary RE Pipeline

Takes a binary file. Runs static analysis (symbols, imports, sections, mitigations), optionally dynamic tracing, feeds the decompiled output to the LLM which selects an exploit technique and generates a working pwntools script. Outputs a structured HTML report with the full reasoning chain.

Supports ELF, PE, Mach-O, APK, WASM, Go, Rust, .NET, EVM, and SQLite formats.

binoracle triage ./binary
binoracle pwn    ./binary

CVE Engine — Autonomous Exploit Development

The CVE engine is a fully autonomous exploit-development pipeline. It receives a CVE identifier and, without any analyst-supplied hints, derives a working proof-of-concept, verifies it in an isolated Docker lab, and emits a self-contained HTML report with Playwright screenshots.

 NVD / NIST          LLM local           Source code         Docker lab         Playwright          HTML report
 CVE descriptor  ──▶  Qwen 2.5 Coder  ──▶  static scanner  ──▶  ephemeral env  ──▶  screenshots    ──▶  disk only
                      zero hints           deterministic        Docker Compose      each step           HTML+CSS

How it works — 7 stages

StageWhat happensComponent
1 · NVD fetch Retrieves the CVE record (CVSS score, affected version, plain-language description) from NIST/NVD plus any GitHub advisories or Exploit-DB entries found in the wild. cve_agent.py
2 · LLM hypothesis The local LLM reads the raw description and proposes a structured exploit plan: vulnerability class (SSTI, SQLi, XSS, RCE…), affected endpoint or parameter, payload strategy, and which Docker scaffolder to provision. No human prompts guide this step. cve_agent.py
3 · Source-code download The engine downloads the exact vulnerable version of the package (WordPress plugin, PyPI/npm/Composer/RubyGems package, or CMS) from its public registry and caches it locally. cve_agent.py
4 · Deterministic scanner A static scanner reads the source code — no LLM at this step — and traces the injection path deterministically: it locates the REST/AJAX endpoint, the DB write, the render context (href, html, js_innerHTML, url, js_string), and derives the exact payload transform needed (e.g. base64-encode for WP REST API). This is the layer that catches render contexts the LLM might miss. websource.py
5 · Docker lab Spins up an ephemeral Docker Compose environment scoped to the CVE: the right CMS version, the right DB, the right plugin or package. For WordPress CVEs this includes wp-cli installation, plugin activation, and subscriber/admin user creation. The lab is torn down automatically after the run. wpverify.py
6 · Headless browser verification Playwright drives a real Chromium instance to execute the exploit: injects payloads via the REST/AJAX endpoint as a low-privilege user, then loads the admin view and checks whether the XSS fires (document.title marker), the SQLi leaks data, or the SSRF reaches the internal host. Captures a screenshot at every verification step. wpverify.py
7 · Report Emits a self-contained HTML report to disk: executive summary, CVSS score, full LLM reasoning chain, winning payload, step-by-step Playwright screenshots, complete curl / Python PoC, and remediation guidance. report.py
Deterministic scanner vs. LLM. The two layers complement each other. The LLM identifies the vulnerability class and rough attack surface. The deterministic scanner reads the actual source code to find the exact endpoint, DB table, column name, payload transform, and render context — without hallucinating. Only the scanner output is used for the actual exploit attempt.

Binary RE Engine — Reversing & Exploitation

The binary RE engine takes a binary file and autonomously produces an exploit chain, decompiled output with LLM annotations, and a structured HTML report. It covers 50+ exploit techniques across all major binary formats. All analysis runs locally — the binary is never uploaded anywhere.

 Binary input
     │
     ├── 1 · Static triage ── checksec, symbols, imports, section layout, entropy scan
     │
     ├── 2 · Multi-backend decompile ── Ghidra / radare2 / angr / pwndbg (auto-selected)
     │                                   + LLM annotation of decompiled pseudocode
     │
     ├── 3 · Vuln pattern detection ── taint analysis, dangerous sinks, format-string calls,
     │                                  integer overflows, UAF patterns, stack smashing hints
     │
     ├── 4 · Technique selection ── LLM picks the right primitive based on mitigations
     │                               (NX/PIE/RELRO/canary) and gadget availability
     │
     ├── 5 · Dynamic (optional) ── strace / ltrace / gdb automation, crash triage
     │
     └── 6 · Exploit generation ── pwntools script, gadget chains, shellcode (bad-char filtered)
                                    + self-contained HTML report

Exploit chain generation

The engine selects an exploit primitive based on detected mitigations and available gadgets, then generates a complete pwntools script.

FamilyTechniques
Stackret2win, ret2libc, ret2plt, ret2csu, SROP (x86-64/x86-32/aarch64), stack pivot, ROP chains
Heaptcache dup, fastbin dup, UAF, double-free, House-of-Force/Spirit/Orange/Mind, large-bin attack, Botcake
Format string%n arbitrary write, GOT overwrite, canary leak, PIE leak
Low-levelshellcode (NX off), bad-char scrubbing, IO_FILE exploit, DL-resolve, GOT hijack
Canary bypassleak + reuse, fork brute-force
PIE bypasspartial overwrite, leak chain
Technique selection logic. The LLM reads the mitigation report and the decompiled output together. If NX is on it uses ROP; if PIE is on it adds a leak gadget first; if a canary is present it looks for a format-string leak or fork brute-force; if the heap allocator is ptmalloc it selects the right House-of-X variant based on libc version. The pwntools script is emitted with inline comments explaining every step.

Reports

Every CVE investigation and binary analysis writes a self-contained HTML report to disk. Reports are single-file HTML with embedded CSS — no external dependencies required to view them.

SectionContents
Executive summaryCVSS score, severity rating, affected component and version
HypothesisFull LLM reasoning chain showing how the exploit was derived
LabDocker Compose specification, service versions, network configuration
EvidencePlaywright screenshots captured at each verification step
PoCComplete, runnable curl / Python / pwntools exploit code
RemediationSpecific fix guidance with before/after code examples
 
# Open report immediately after run
binoracle cve CVE-2025-27516 --open-report

# Write to a specific directory
binoracle cve CVE-2025-27516 --out ./reports/

# Batch with output directory
binoracle cve-batch CVE-2025-27516 CVE-2024-23334 --out ./reports/

MCP Integration

binoracle exposes its full toolkit as an MCP server, making all analysis capabilities available to any MCP-compatible client: Claude Desktop, Cursor, Zed, and others. The server runs locally and does not require network access.

binoracle mcp-server

Add to your client configuration:

{
  "mcpServers": {
    "binoracle": {
      "command": "binoracle",
      "args": ["mcp-server"]
    }
  }
}
